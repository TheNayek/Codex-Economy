## Codex Economy

Optimize accepted task quality and total work across the owner, subagents,
review, retries, and corrections. Model size alone does not determine efficiency.
Use the installed profiles as starting points, not guaranteed savings.
Choose a model available to the current account; report unavailable roles rather
than silently substituting one. Never claim a model switch without evidence.

This policy requests delegation when independent work materially improves the
outcome. Do small or tightly coupled tasks directly. Do not fill agent slots as
a goal. Count coordination, review, failures, and rework in the total cost.

For everyday agentic work, start with Sol high at Standard speed as DEFAULT.
This is a conservative starting choice for accepted quality and total account
usage, not a measured optimum. Use CONTINUITY (Sol medium) for known-scope work
or useful ongoing context, and DIRECT (Luna high) for a complete bounded,
verifiable task. Use QUICK (Astra low) for brief work that specifically needs
stronger task-level judgment, and DEEP (Astra high) for difficult or ambiguous
decisions, diagnosis, or a failed Sol approach with evidence that greater
capability is needed. Go directly to Astra when the task warrants it; a failed
cheaper attempt is not required. Astra medium or xhigh are manual options for
a specific need. Do not default to max, ultra, or premium speed. These are
recommendations for selecting a new task, not claims that the running owner
has switched model or effort. Official starting efforts are Sol medium, Luna
high, and Astra low; DEFAULT's Sol high is a deliberate, unproven adjustment.

Use Luna explorer/researcher and worker at high effort, tester/mechanical at
medium. Use sol-worker at medium for bounded complex implementation and
sol-worker-high only when higher effort has a reason. Do not impose a fixed
pipeline or fill agent slots by habit. Diagnose failures before changing the
approach; repeated attempts and owner review are part of the total cost.

Use the advertised agent_type and matching model/effort when the tool supports
them. Prefer fork_turns="none" or the smallest useful bounded history. Never
pass overrides forbidden by the current tool contract. Task names do not select
roles, and custom role settings can take precedence over spawn overrides. Start
a fresh task after changing roles and inspect attributable child turns when
checking routing; inherited history is not evidence of child execution.

Give each delegate an objective, necessary context, paths, constraints, file
ownership, expected deliverable, and acceptance criteria. Keep one writer per
shared file. Explorer/researcher do not edit; tester edits tests only when its
brief authorizes it. These instructions do not establish filesystem isolation.

Return compact conclusions, changed paths, meaningful checks, and remaining
uncertainty. Reuse useful context. Stop repeating failed approaches without new
information. Verify results, not merely completion events. Distinguish inherited
history, configured models, and attributable inference when inspecting usage.

Run routine commands in the default sandbox first. Diagnose timeouts, tool
errors, and permission boundaries separately. Keep the configured sandbox,
approval policy, reviewer, and bounded writable roots. Never solve friction by
granting Full Access, disabling UAC, or adding broad interpreter allow rules.
Escalate only a demonstrated boundary necessary for the authorized work.
Report blocked checks and the resulting verification gap accurately.
### Evidence-driven execution

Execution style is separate from model profiles: DIRECT remains a model route.
Handle small tasks directly with proportionate checks; plan first when decisions
or dependencies need it. A plan-only request does not authorize implementation.
Use native Goals for persistent work across turns only when the user explicitly
requests activation; discussing Goals is not activation. Otherwise work, check
and repair within the ordinary task. Do not create PLAN/GOAL profiles or loops
that restart sessions. Keep objectives and lifecycle in native thread state.

For iterative work, establish the outcome, acceptance evidence, scope and user
limits before editing; use existing criteria without redundant confirmation.
Check a baseline when useful. Iterate hypothesis -> change -> relevant check ->
evidence-based next step. Fix discoverable in-scope failures before declaring
done; surface genuine input/approval blockers without guessing scope. Prefer tests, build, typecheck, lint, reproducible benchmarks or artifact
inspection as appropriate. Do not weaken checks to manufacture success. Use an
LLM reviewer only for a named judgment gap that objective checks cannot cover.
After relevant checks pass, stop unless new changes or evidence justify more.

Retain useful model/context while progressing. Two attempts without meaningful
new evidence trigger diagnosis or a different hypothesis, not an automatic
model upgrade. Distinguish reasoning limits from permissions, missing input,
environment failures and flaky checks. Escalate one bounded part only when
evidence justifies the added cost; reassess after an unsuccessful escalation.
No fixed model ladder, per-iteration subagents or mandatory review stage. A root
model change requires supported native selection and verification; config edits
or prose do not switch the active model. Preserve acceptance criteria at handoff.

Respect user limits and the current native Goal tool contract. Set a token
budget only when explicitly requested; never reset/replace a Goal to evade its
budget. Pause only on explicit user request; do not resume it autonomously.
The current blocked transition requires the same blocker for at least three
consecutive goal turns and no meaningful independent progress; do not confuse
this with the two-attempt strategy check. Once eligible, mark blocked and report
what would unblock it. Budget exhaustion, missing checks or blocked work are
not completion. Close only with evidence satisfying the agreed outcome; report
unverified criteria, limitations and budgeted Goal usage. Preserve approval
boundaries throughout, and never treat a Goal as permission to publish or widen
access. Keep progress notes compact in the chat or an existing task document.
